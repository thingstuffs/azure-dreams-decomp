# 8196096C: aggregate accesses remove the scheduling fence

## Result

Claude's reverse scalar/aggregate hypothesis produces a fence-free exact US
candidate for `dungeon/func_8196096C` (true function `func_8002616C`).
The reviewable source is `docs/evidence/8196096C_aggregate_candidate.c`.
This is evidence for a sufficient ordinary C representation, not proof that
its spelling or field names reproduce Konami's original source.

Two source changes are necessary in the tested forms:

1. Use the existing `Bank56_8196096C_Scratch` pointer from the first draw-depth
   store, writing `scratch->value` at offset 0x20. Keep that same pointer for
   the subsequent scratchpad setup. The previous reconstruction used a
   separate `s32 *scratch_words` for the early store and initialized the
   struct pointer after `func_800649A0()`.
2. Read the texture record through struct fields: halfwords at offsets 4/6,
   bytes at offsets 8/9/10/11. The previous reconstruction read the halfwords
   with `*(u16 *)(texture_config + offset)` through a byte pointer.

Remove `ODDITY_SCHED_FENCE()`. The existing `extern u8 D_80027374[12]`
declaration can remain compatible with the rest of the module: the candidate
casts its address to a 12-byte `TextureConfig *` locally.

## Mechanism: combine changes address knowledge, sched1 adds the edges

The exact result is caused by real store-to-load dependencies in the first
scheduling pass. It does not require sched2 to repair an earlier order.

The target-only RTL establishes both inputs to that dependence decision:

- Old cast halfword reads produce plain `mem:HI`. Texture struct fields
  produce `mem/s:HI`, setting `MEM_IN_STRUCT_P`.
- With the old split scratch setup, scratch pseudo r92 is initialized by
  UID 51 to `0x1F800000` and retains a `REG_EQUAL` constant note through
  combine. With the shared early scratch setup, UID 33 initializes the same
  pseudo to the same constant. Its note exists in cse, cse2 and flow, but
  disappears in combine. The numeric initialization itself is unchanged.

`toolchain/gcc-src/2.7.2-cdk/sched.c:419-453` builds its known-value table from
`REG_EQUAL`/`REG_EQUIV` notes. Without the note it leaves the pseudo represented
by itself. Thus the shared early setup leaves sched1 without a canonical fixed
scratchpad address, even though a human can read the constant assignment.

`true_dependence` in that file, lines 832-861, canonicalizes both accesses and
checks both address conflicts and the scalar/aggregate exception. A varying
non-byte aggregate access is exempted from conflict with a fixed scalar access.
This explains the interaction:

| Scratch address knowledge | Texture halfword representation | Outcome |
| --- | --- | --- |
| Fixed (old split setup) | scalar | disjoint addresses; loads can move |
| Fixed (old split setup) | aggregate | disjoint addresses; loads can move |
| Unknown (shared early setup) | scalar | scalar/aggregate exemption; loads can move |
| Unknown (shared early setup) | aggregate | conservative dependency; stores stay first |

In `mechanism/both_ptr/both_ptr.sched`, **within `func_8002616C`**, UID 218 is
the first texture load (`mem/s:HI`, r96 + 4). Its true-dependence LOG_LINKS
include UIDs 199, 202, 207 and 212: the four scratch stores at offsets
120, 112, 128 and 136. Root independently read these exact RTL records.
The corresponding store sequence is followed by `lhu $2,4($4)`, as in retail.

This traces the causal boundary to combine's removal of the address note;
it does not claim to have audited every internal combine action leading to
that removal. The representation does not make the physical objects overlap:
it changes what this compiler can prove about them at scheduling time.

Native dumps contain many functions with reused UIDs. The generated whole-module
`why_sched_b2.txt` summary mixes those identifiers and is not used as evidence;
the raw target-function RTL is authoritative here.

## Regional scope and diagnostic limits

The paired JP body is 936 bytes and remains unmatched. Under stock 2.7.2,
the no-fence old source and the combined aggregate candidate produce
byte-identical unlinked function bodies; masked JP distance is 113 for each.
Under CDK the masked JP distances are 235 for no-fence and 236 for the combined
candidate. This is not a JP improvement or a full JP validation. The CDK US
candidate is validated by the separate full native byte gate above.

The paired retail extents used are US DUNGEON_DUNGEON.BIN offset 0x198096c,
872 bytes, and JP offset 0x1981a94, 936 bytes, from the existing local
`r118_sol61_variants/extracted` containers. These were read by bounded extents.

Two diagnostic traps were checked:

- `lab.py baseline` reports zero pins here and its automatic pin-erased
  variant retains `ODDITY_SCHED_FENCE`. The controls explicitly remove it.
- The lineage heuristic flags the absolute scratchpad store as a <=2.7.2
  feature. That single assembler-macro store is insufficient to reject CDK:
  the rest of the listing uses CDK's split address generation, the registered
  native build matches exactly, and genuine PsyQ 4.1 agrees.

The previous universal no-C/floor conclusion for this function is superseded
by a concrete counterexample. Neither that conclusion nor an analogy with
800A1020 alone establishes a scheduling mechanism.
