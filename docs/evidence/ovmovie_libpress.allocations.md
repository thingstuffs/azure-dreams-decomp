# Native LIBPRESS object and separated allocations

Review pending. The single combined package supplies recovered rows, tools and module sources together.
This package activates a complete seventeen-function native TU at ordinary 2.7.2-G0.
It owns 169 string bytes at file 0, 1888 text bytes at 0xED8, and 332 writable-data
bytes at 0x1A3C. One compiler invocation and both assembler legs reproduce all 2389
semantic bytes. There are no masks, per-function placement directives, or raw payload
substitutions. The original SDK object establishes the private/public membership.

The new native allocation model accepts literal const strings, u32 arrays/plain
records and aligned PSX device pointers. It verifies every declared storage symbol,
natural code order, all allocated sections, literal bytes and exact imports. GNU
trailing alignment padding is removed only at section end, only when its exact
extent follows the ELF alignment, and only when all removed bytes are zero. The
retained bytes must equal the C declarations and genuine storage. Here that is three
rodata bytes and four data bytes. LNK omits private data debug names; complete storage
and fully resolved code relocations verify those offsets. Exported symbols cannot
use that omission rule.

Production windows physically project both owned storage allocations from the new
whole-object build, with separately retained unowned gaps. A storage allocation
cannot overwrite a registered C segment or multiple unrelated source segments.
Certification replays padding, ownership and both objects from the bound artifacts,
and checks complete storage projection. An unchanged member candidate still uses
the full physical TU; an incorrect return is rejected. Shared includes cannot change
through a per-member candidate. Other native models retain their strict old paths.

The resident map is a guarded consolidation of the preceding narrow rowbase proofs.
All registered definitions are at the observed true identities. The library source
keeps seven helpers and owned storage static. Game data ownership remains outside
this module; the complete game text candidate is not activated by this package.
