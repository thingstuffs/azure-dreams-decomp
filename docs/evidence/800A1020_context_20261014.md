## Latest result: scalar-global C matches US, JP and EUR without a fence

**Supersedes the unresolved verdicts below.** Delegated source-context research
found that declaring the preservation flag as an external scalar, rather than
an array or a local pointer into a constant page, makes ordinary C byte exact.
The reviewable source is `docs/evidence/800A1020_scalar_candidate.c`.

the state-page pointer and the existing decision. It has no fence, volatile,
register pin, extra branch, helper, or loop. Existing sibling functions already
declare the same flag as a scalar. This supports the source shape, although it
does not recover the original identifier or exact original source text.

### The missed mechanism is in the second scheduling pass

The earlier claim that sched2 cannot repair sched1's ordering was conditional
on the reconstructed pointer/array representation. It is false for the scalar:

1. In sched1, both the scalar and array variants still place the flag clear
   before the mode load. The solution does not need a new sched1 barrier.
2. After register allocation, the state load is a varying-address `mem/s:SI`
   reference. The scalar flag remains a fixed symbolic `LO_SUM` reference,
   without the `/s` (`MEM_IN_STRUCT`) marker. Array `[0]` retains that marker.
3. cdk `sched.c:852-861` exempts a varying non-QI aggregate reference from
   conflicting with a fixed non-aggregate reference. This removes the
   conservative store/load dependency for the scalar case. The same test is
   present in anti/output dependence. The array case fails the exemption.
4. Sched2 can consequently move the scalar store after the mode load; delay-slot
   filling places it in the first branch's slot, exactly as retail does.

The expansion paths marking aggregate accesses are visible in cdk
`expr.c:5341-5351` (pointer arithmetic) and `expr.c:5748` (array/component
reference); the decisive evidence is the scalar/array pass-dump comparison.
Both addresses being recognizable in sched1 did not justify assuming the same
dependence graph after hard-register allocation in sched2.

Detailed delegated reports and controls are in
`work/native_lane/a1020_research_20261014/{context,scheduler,controls}/REPORT.md`.
The reconstructed floor-setup struct is a valid semantic control but cannot
establish the original object declaration. One attempted separate floor-symbol
probe had the wrong address/width and is excluded, not counted as a negative.
A subsequent independent investigation also resolved 8196096C with combined
aggregate texture accesses and shared scratchpad setup. See
`docs/evidence/8196096C_aggregate_20261014.md` for its separate byte gate and
mechanism; the 800A1020 result alone did not establish that conclusion.

The live source, oddity ledger and recipe remain unchanged: this turn was
authorized as research. The exact candidate and evidence are ready for the
normal landing workflow. The old universal no-C claim for 800A1020 should no

### The flag preserves sound sequences across transitions

This is supported independently of the instruction match:

- `src/town/func_800C37F0.c` sets this exact byte, D_80080A88. Its recovered
  developer script symbol is `S_set_no_change_seq` (table slot 33;
  `config/names.tsv`, `docs/SYMBOLS.md`, `include/script_symbols.h`).
- All four visible calls to func_800A6780 ignore its return value. They occur
  in `src/dungeon/func_8008D990.c`, `func_800C627C.c`, `func_800C0848.c`, and
  `func_80D6A4D8.c`, immediately before incrementing floor state and entering
  the transition. Some prototypes already declare it void; this does not
  prove its original return type, since retail explicitly produces 0/1.
- `src/slus/w_80040AA0.c` clears D_80080A88 for a changed transition category,
  then, when the flag is zero, queues SD_Call(0xCF) and processes sound
  commands through func_800542BC.
- `src/town/func_800C3ACC.c` uses the same flag to avoid restarting an unchanged
  sound selection. `src/slus/konami_runtime_w_8003BAF8.c` sets it when the
  next selection pair matches the current pair.
- Floor setup (`src/dungeon/func_80285E80.c`, true func_80018E80) computes
  `D_8008146C[0] / 5`, then selects resource `group + 1` through func_80019684.
  That loader (`src/dungeon/func_80286684.c`) returns 1 immediately when the
  requested resource is already active. Floor setup resets the preserve flag
  when the loader returns zero and performs the sound transition as needed.

The owner independently describes ordinary ascents, after choosing to continue,
as a black-screen transition with music retained except around five-floor
boundaries; monsters/textures/graphics also change at those boundaries. This
supports a shared floor-group concept. It does NOT establish that the specific
buffer loaded by func_80019684 contains all those asset classes: its sound
commands and preservation flag identify an audio role, while monster records
are separately loaded by func_800194C4 using the individual floor number.

For nonnegative internal floor N, the tested comparison changes at N=4,9,14,...
when advancing to N+1. Do not equate internal numbering with displayed floors
without checking their correspondence. Mode 1 unconditionally preserves the
sequence; other nonzero modes do not. In floor setup, mode 1 is established
when state_022c==1 and saved floor<2; mode 2 chooses a resource group randomly.
Another mode-2 writer is tile_type==4 in src/dungeon/func_80088290.c. The original
meanings are identified further in the follow-ups below: tutorial and second tower.

### Ordinary inline helpers do not remove the mismatch in the tested forms

The historical explicit helper tests found in r95_inline_probe were for
8196096C, not this row. r118_opus_o8's k_ptr_ptr_inl.c puts the expression
inline in the body; it does not define an inline C function.

22 diagnostic candidates are recorded by probes.py and lab_log.jsonl. They
include page/byte setters, a setter returning its assigned value, a complete
inlined body with constant pointer actuals, page/word/global/output-parameter
mode getters, a floor-group predicate with a step parameter, and a nested
output-parameter group helper. None of the ordinary inline forms is exact.

The page setter, page getter and simple group predicate retain the plain
body's US aligned score: 1 substitution + 2 indels, total 3. The byte setter
is total 7; the complete-body helper is total 15. These are bounded negatives,
not a proof about all possible helpers. The .cse and .sched dumps for
inline_page show that parameter copies disappear, constant REG_EQUAL notes
remain, and the opening store/load dependency is absent, as in plain C.
An inline name alone does not preserve opaque pointer arguments.

The simple group predicate matches JP with address-only masked LCS distance
0 at stock 2.7.2, exactly like the plain expression. Therefore the JP match
does not distinguish those source abstractions. It also does not cure US.

### Shared result variables are plausible semantically but currently worse

Probes include a common keep/result local (s32 and s8), reusing mode as the
decision, reusing it as the next-floor value, assigning/returning the byte,
and computing the decision before one final store.

The s32 shared result produces US aligned total 18 (4 substitutions, 14
indels); JP masked LCS distance 22. The generated code carries a result in
$a2 across branches and moves it to $v0 at return, unlike retail's use of
$a2 as the constant 1 and direct return constants. Assignment-return is the
same US total-3 near miss as plain C. Other forms also fail; see the table.

The caller/context evidence supports the preservation decision but supplies
no independent evidence for the invented debugMode arm or a shared local
that would extend flagBase's assignment count. A higher-level shared
floor-group helper remains plausible source, but is not yet a matching lever.

### A diagnostic control-flow boundary refutes the exclusive alias claim

Replace the empty asm fence by wrapping just the mode read:

```c
do { mode = stateBase[0x2090 / 4]; } while (0);
flagBase[0xA88] = 0;
```

`cand/macro_mode.c` is exact at the registered US recipe:

- lab byte scorer: exact, 0 substitutions, 0 indels;
- separate assembly through the reused JP A/B harness: all 116 unmasked bytes
  equal the US retail slice;
- sncheck: assembly identical with genuine PsyQ 4.1 CC1PSX.EXE.

This is NOT accepted here as a recovered source solution. The owner points
out that one-trip forms are another barrier construct previously removed.
No original mode-getter macro has been identified. Wrapping the flag store,
or both flag stores as setters, is not exact (US total 6).

Mechanism: macro_mode.combine retains LOOP_BEG/LOOP_END notes around the lw,
while both page registers still have the same REG_EQUAL constants and single
sets. sched.c:2082-2110 makes the instruction following a loop boundary
depend on prior uses/sets and flushes pending memory operations. The store
therefore depends on the mode load even though alias analysis still knows
their addresses are disjoint. macro_mode_deps.txt shows lw UID17 -> sb UID29;
plain_deps.txt has no corresponding lw -> sb edge. Later delay-slot filling
produces retail's beq/sb pair.

The JP check is adverse but small: stock 2.7.2 gives 35 words, no frame, masked
LCS distance 2, versus plain C's distance 0. The sole movement is `li $v0,1`
from before the flag-clear macro to after it. This does not reproduce both
builds from unchanged source. It would require a source/macro difference or
another independently supported detail; no such difference is established.

Consequently, r118_opus_o8's universal "no pure-C move exists / only an asm
fence orders them" is too broad. Its constant-address alias reasoning still
holds within ordinary straight-line spellings, but scheduler dependencies
also arise from control-flow notes. This experiment provides another such
route besides the already known exact-but-rejected late-dead arm. It is not
evidence that the original necessarily used either construct.

## Follow-up: second tower and specialized shared helpers

The local ad-rando checkout at `ref/adrando` (a local checkout outside this repository), commit
`1a26d643b7726fb30bf207142855eed30e8ceade`, independently identifies the route:

- `fields.js:210` describes the second tower as original postgame content
  inaccessible normally, entered from an elevator on floor 2.
- `constants.js` names the availability-check address 0x800199C8, the true
  address of our func_802869C8 row.
- `util.js:941` (applySecondTower) patches in a type-4 elevator. The original
  tile handler func_80088290 writes mode 2 when using that tile type.
- The original check requires mode 0, floor 2, progression flag 0xA2, and an
  inventory entry of category 0x0C, ID 8. func_800A11C8 (true func_800A6928)
  counts that category/ID combination in the inventory. ad-rando items.js
  names the item `?` and marks it out of the normal pool. Its Blue Collar is
  a different ID; do not infer a named quest item from the gate alone.

Thus mode 2 is a runtime second-tower state, not a build-time switch. Its
inaccessibility to an ordinary player does not let this compiler eliminate
the code: the gate depends on runtime globals, inventory and function calls.
This does not rule out specialization of a shared helper *inside* a path
where the compiler already knows mode==0.

Eight probes in shared_probes.py test that narrower hypothesis. Four define
an inline selector: tutorial -> group 0, second tower -> RNG & 7, otherwise
floor / 5. They vary s32/s8 mode parameters and passing literal 0 versus the
outer mode, and invoke the selector twice under the original mode==0 guard.
Other probes reuse the floor/group local, expose a redundant mode-2 clear,
spell the policy as a switch, or put the full predicate into an inline helper.
These are source hypotheses, not recovered original definitions. None is exact.

The literal-mode selectors score US aligned total 3 (1 substitution, 2
indels), but this is NOT the same emitted body as the earlier total-3 plain
candidate. The selector candidates reserve a 16-byte outgoing-call area even
though no calls remain. Their clear still precedes the mode load, and their
stack adjustment occupies the branch delay slot. Retail has no frame. Raw
cc1 output, the lab diff and the independent A/B assembly all agree. With
stock 2.7.2, the checked s32 constant selector has a frame too and JP masked
LCS distance 3; the checked s8 runtime selector likewise has a frame.

The constant s8 dump has inlined RNG calls in RTL, none in the first jump
dump, and constant-page REG_EQUAL notes still present at combine. The
runtime s8 candidate also has neither calls nor opaque page pointers left
by combine. In these shapes the unused branches disappear before sched1
and do not supply the needed opening memory dependency. Their lexical
BLOCK_BEG/END notes are not equivalent to the LOOP_BEG/END dependency found
in the diagnostic do/while probe. The retained call-area requirement is
additional evidence against these particular RNG-bearing inline shapes.

The context supports sharing *music resource-group policy*, but not a
single five-floor selector for every asset class. Ordinary monster records
and a theme byte are loaded per floor by func_800194C4, separately from the
music-group loader. ad-rando util.js:853 additionally comments that vanilla
themes change on even-numbered floors. This comment is supporting context,
not an independent extraction of every retail theme-table entry.

Current judgment: second-tower identity is established, and a shared policy
abstraction is plausible. It has not explained the scheduler oddity. A
successful source explanation must affect the opening mode-read/flag-clear
dependency or register assignment accounting at sched1, without leaving
extra calls, stack adjustment or policy branches in retail. Removed game
content alone does not satisfy that condition. A smaller transition-state
accessor/setter remains a better-targeted search than importing the whole
randomized resource-selection routine. Neither the macro nor shared-local
angle is proven impossible; neither currently supplies a supported replacement.

## Follow-up: wider JP comparison and remaining investigation paths

The owner supplied Claude/Sonnet's broader comparison: all 29 route-ID
readers/writers retain their logic between JP and US; tutorial data is
byte-identical; all ten target call sites agree and ignore the return value.
The actual report was subsequently read at
`work/native_lane/r118_sonnet_routediff/REPORT.md`. Its ten call sites are the
same four distinct callers previously inspected plus overlay copies. The
comparison covers DUNGEON, not every executable/container in the game.
It strongly weakens a US-only tutorial/route branch, without proving identical
preprocessed C, declarations or build settings across the releases.

Two additional pass-isolation compiles use the existing plain candidate:

- `dumps/no_sched1/plain.s`, cdk -O2 -G0 -fno-schedule-insns: the opening
  mode load, compare and delay-slot flag clear have retail's order. The
  division region changes register allocation and instruction order, so
  this is not a solution or a proposed recipe change.
- `dumps/no_sched2/plain.s`, cdk -O2 -G0 -fno-schedule-insns2: the early flag
  clear remains wrong. This does not fix the ordering in question.

These are raw assembly observations, not newly scored byte-distance claims.
The useful remaining paths are to establish a recurring boundary/source idiom
across the two fence rows and suitable matched controls; audit compiler-pass
behavior and actual module build context against those controls; or find
independent source-structure evidence in another available build. Merely
turning off scheduling globally fails the division-region constraint.
Header/declaration and original module context are still worth auditing, but
ordinary symbol/page spellings and elementary inline helpers already have
bounded negative results. Function adjacency alone is not evidence of a
compiler effect, and any proposed effect must be demonstrated in pass dumps.
