## Result and scope

retail body was read and disassembled: `root/retail.{bin,asm}`.

  compiler-split store at word 52/56 supports the cdk/2.8.x family;

- The ordinary lane baseline initially reported `no pinned object cached`.
  That was a harness limitation. `bytegate/score_variant.py` now compiles and
  links in a private SlusView and compares the complete emitted function to
  the frozen retail body. Exactness requires size 336 and byte equality.

Use `bytegate/results/*_fixed.json` for final receipts. Earlier receipts were
superseded after fixing relocation-reporting and variable-length extraction.
The scorer's nonzero alignment metric is explicitly SequenceMatcher based,

## Retail site map

Frame: 24 bytes, saved ra and s0. Switch order: main case zero, 0x1000,
0x2000, 0x4000, common epilogue; the latter three share the command call.

| Register | Role |
| --- | --- |
| a0 | incoming message, then second packed offset, then later call arguments |
| v0 | returned record pointer, then both tag-extraction temporaries |
| v1 | first packed/decoded offset, then flags |
| a1 | record's base adjustment |
| a2 | 0x00FFFFFF mask |
| a3 | playback-state pointer D_800847D0 |
| t0 | high-address component for D_800847D0 |
| t1 | record's low halfword, retained for the later signed argument |
| s0 | task pointer D_80084858 across calls in the activation path |

Record reads are lhu +0, lw +4, lw +8, then lw +12, with the first raw-state
store between the final two loads. Both packed values are stored raw, masked,
and adjusted. Their high bytes are saved separately. The first adjustment is
-0x20 + base; the second is +0x20 + base. All these stores and the dispatch
branches are part of the byte target, even where a more compact C spelling
might let an optimizer discard an intermediate store.

## What the compiler evidence actually shows

The unpinned local-allocation replay reproduces **22/22 local pseudos**:

| Quantity | References | Lifetime indices | Priority | Assignment |
| --- | ---: | --- | ---: | --- |
| record pointer | 5 | 8..26 | 5555 | v0, call-result copy suggestion |
| first offset | 11 | 20..40 | 16500 | v1 |
| second raw/masked/final value | 11 | 26..60 | 9705 | v0, ordinary priority pass |
| base | 5 | 18..58 | 2500 | a0 |
| first tag | 2 | 28..38 | 2000 | a1 |
| second tag | 2 | 46..54 | 2500 | v1 |
| mask | 3 | 6..48 | 714 | a2 |

**Important precision:** the record and second value are different quantities.
The second quantity has no copy suggestion. It takes v0 in the priority pass
because the pointer's lifetime has just ended. It does not inherit the
pointer's copy preference. Raw second and its final result *are* combined into
one allocation quantity. This distinction matters when choosing a source fix.

With the pin, second is already hard a0, and its later arithmetic has a0
suggestions. Base receives a1 and both tag temporaries can use v0. The pin
therefore changes allocation constraints and quantity relationships, not just
one final register name.

The front half of sched1 is the same in the current pinned and erased forms:
base load UID42 precedes first-offset load UID45, followed by raw store50,
second load53 and first tag shift55. **The visible base/first load reversal
appears in sched2 after allocation**, not in sched1 for these current controls.
There is nevertheless a sched1 difference in the second-tag tail: pinned tag
store91 precedes masked store94/add97; erased tag store89 follows masked
store92/add95. Thus it would be wrong to say the entire first-pass schedule is
identical. Root independently checked the raw dumps.

Primary receipts: `mechanism/lreg_{erased,pinned,base_late}_receipt.txt`,
`mechanism/sched_uid_comparison.txt`, and the raw target dumps under
`mechanism/dumps/{pinned,erased}/`.

## Follow-up: falsifiable decoder/helper interface test

User asked how to test the helper theory. A bounded interface comparison is
saved under `work/native_lane/w54b08_research_20261014/helpers/`.
Each helper performs actual tag extraction, low-24-bit decoding, or pending
state publication. The tests use the current registered compiler and remove
the register pin. They add no volatile, assembly, artificial barrier, dead
branch or cancelling arithmetic.

| Contract | Listing distance | Interpretation |
| --- | ---: | --- |
| No helper, erased control | 30 | reference |
| Tag/offset expression macros | 30 | no relevant representation change |
| By-value second decoder, publishes raw/masked values and returns adjusted offset | 22 | repeats prior helper control; allocation changes but wrong |
| In-place decoder taking address of local second value | 41 | frame grows 24 to 32; stack stores remain |
| Pure decoder returns `{offset, tag}` struct | 74 | frame grows 24 to 40; aggregate stack copies remain |
| Pure decoder writes offset/tag through output pointers | 38 | extra local storage/operations and wrong allocation |
| Both first and second words use that output-pointer decoder | 76 | no match |

The by-value replay reproduces 23/23 local pseudo assignments. It merges mask
and decoded/final result into quantity 0, priority 5555, a0. The raw second
and its shifted tag are quantity 5, priority 4615, v0. The first tag is a2.
Thus getting the *decoded result* into a0 does not solve the required raw
second load into a0. `helpers/by_value_alloc.txt` is the actual receipt.
The output-pointer replay reproduces 22/22 and likewise remains inexact;
`helpers/out_pair_alloc.txt` records it. Tool columns labelled retail in these
`--retail none` replays are not independent retail mappings.

Acceptance checks for any further helper hypothesis:

1. Preserve actual decode semantics and the observed memory accesses; the
   function still needs its 24-byte frame and observed saved-register set.
2. Inspect CSE/combine and local allocation. Require an explained change to
   the raw second value's v0 conflict, the tag's lifetime/priority, or a real
   copy preference. Type/helper names alone provide no evidence.
3. Verify raw second=a0, base=a1, mask=a2, and tag temporaries=v0 together.
   Then inspect sched1 and sched2 for the required loads/stores and delays.
4. Only a complete candidate advances to the private 336-byte retail link
   gate and genuine compiler cross-check. None of this batch qualified.

An inline helper's first formal parameter is **not automatically assigned a0**:
there is no emitted call boundary establishing that ABI requirement. A helper
can help only through the expanded compiler representation and its actual
allocation constraints. A real out-of-line helper call at the decode site is
not supported by retail, which contains no such call.

These negative results reject the listed interfaces, not all possible helper
source. A next experiment needs a specific predicted lifetime or quantity
change beyond these controls; general helper plausibility is insufficient.

## Follow-up: derive the needed lifetime change before choosing helpers

Package: `work/native_lane/w54b08_research_20261014/inverse/`.

The standard inverse CLI tests one wrong quantity at a time while preserving
already-correct quantities. Its output alone is not proof that all incorrect
roles are repaired together. `full_goal.py` therefore separately replays the
existing allocator model with **all eight block-7 quantities constrained**:
mask=a2, record=v0, base=a1, first=v1, second=a0, both tags=v0, flag test=v0.
The unmodified replay first reproduces all 22/22 local pseudos.

With every other model input held fixed, each of these single changes meets
that full local-register goal:

- second quantity birth 26 -> 25 (overlap the record lifetime);
- second quantity death 60 -> 63 (overlap the flag-test quantity);
- first tag references 2 -> 5;
- second tag references 2 -> 4;
- first tag birth 28 -> 36, death still 38;
- give second a genuine a0 copy suggestion.

**All are counterfactual diagnostics, not C candidates or byte matches.**
Indices are allocator half-instruction positions, not machine cycles.
In particular birth25 is an early-clobber-style boundary, not evidence that
an ordinary load can be assigned such a constraint by changing its spelling.
Changing real C can alter several lifetimes, counts and priorities together;
one may not carry these thresholds across a different allocation table.
Results are in `inverse/full_goal_results.json`.

Three ordinary source translations were then tested:

| Source prediction | Listing distance | What survives |
| --- | ---: | --- |
| Compute flag condition before publishing final offset | 30 | scheduler restores second death60 and flag-test birth62; no overlap |
| Inline publisher returns computed condition | 30 | same allocation geometry; wrapper does not establish a dependency |
| Keep raw first word and extract tag at publication | 29 | raw/tag quantity becomes 4 references, length12, priority6666; second is priority9166 and still wins v0 |

These are narrower negatives than "helpers fail". The first two explain why
source statement order does not impose the desired lifetime. The third shows
that a useful raw-word snapshot really changes allocation statistics, but
not enough, and adds an instruction. Its arithmetic cannot be declared solved
from the priority change alone. Replay fidelity is respectively 22/22, 22/22,
and 23/23; see `inverse/*_alloc.txt`.

Next tracked question for W54B08-COPY-LIFETIME: locate the exact optimization
that removes the required overlap/copy in a context-supported decode or
publication interface, and change that interface only when it predicts the
needed retained RTL. The helper theory is now a set of specific lifetime and
preference hypotheses, not a mandate to enumerate wrappers. No production
change or whole-function match resulted from this follow-up.

## Follow-up: publication context and the actual delay-slot refusal

The surrounding sound routines support a pending/active cue model. B08 writes
pending words at +10/+14 and tags at +31/+33. `80054C58` snapshots and clears
those fields, transfers them to active +08/+0C and +30/+32, and clears the
transition flags. `80054CD4` then starts CD commands from the active fields.
`80054E00(E4)` saves/clamps the CD position into +18 and publishes that position,
the active endpoint, and active tags back into the pending fields. Both E4 and
B08's deferred path request task state 2 at `D_80084864` (+0C of `D_80084858`).
This is evidence for shared transition behavior, not proof of an original
helper or nested C struct. In particular the unconditional endpoint store does
**not** semantically require its register to stay live through the flag test.
See `tail_context/REPORT.md` in the research package.

The previous isolated lifetime counterfactual needs a stronger qualification.
An actual swap of the final store and flag test changes BOTH quantities:
second death60 -> 62 and flag-test birth62 -> 60. Replaying them together drops
the test priority from 10000 to 5000; the second quantity at priority9166 still
wins v0. Base remains a0 and the tags remain a1/v1. Thus merely retaining the
requested source order would not solve the register allocation, even if
sched1 allowed it. `tail_roles/joint_tail_geometry.py` reproduces the 22/22
baseline and records the joint diagnostic in `joint_tail_geometry.json`.
This does not invalidate other independent allocation routes, such as a real
copy suggestion or different tag priorities; it closes the tail-swap-only route.

The decisive final-store movement was independently traced in the real CDK
compiler's delay-branch pass, with `dbr.py` under gdb:

* Erased UID120 branch: UID116 `sw $2,20($7)` is explicitly rejected because
  it reads v0, which UID118 `andi $2,$3,0x0400` sets. The pass instead takes
  the following flags OR into the delay slot.
* Pinned UID126 branch: UID122 `sw $4,20($7)` is accepted in the backward
  scan and fills the slot, matching retail.

Both traces reproduce the plain compiler assembly and all 18/18 final delay
instruction outcomes. Receipts: `tail_roles/dbr_erased.txt` and
`tail_roles/dbr_pinned.txt`. The final offset and flag test are **separate
allocation quantities reusing v0**, not coalesced quantities. Their physical
register conflict explains this store-order difference after allocation.
There is no need to posit a hidden fence to explain that particular effect.

Three further legitimate scratch-role controls were measured with Lab:
shared tag/test scratch distance50; decoded carrier reused for a later flags
read distance57; decoded carrier assigned an earlier flags snapshot distance30.
The snapshot form reproduces the baseline allocation (22/22 replay). The
shared tag/test form changes allocation (19/19 replay) but leaves second in v0
and moves mask to a1. No candidate matches or supersedes the prior frontier.
The scheduler agent also measured direct flag-field access after publication
at distance27; its final offset remains v0, and it is not a new best candidate.

W54B08-COPY-LIFETIME remains routed to C rebuild, with a narrower acceptance
criterion: explain a natural source relationship that changes the raw-second
allocation while preserving base=a1, mask=a2, and tags=v0. A helper qualifies
only if its expanded RTL supplies that change. The final delay-slot store is
a downstream check of the allocation, not an independent source-order target.
No production source, shared header, recipe, or ledger was changed in this
follow-up, and no byte-exact pin-free solution is claimed.
