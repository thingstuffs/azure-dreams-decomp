# Partition-aware SLUS certificate: read-only checkpoint

This is a design handoff, not a certificate or a change to the placement ladder. The immediate question is how to certify a destination module's **complete physical translation unit** after a collector contributes functions to it, without treating one moved function as proof of the entire collector row.

## Current assumptions and exact call sites

`tools/slus_module_context.py:68-79` already computes a partition-connected fingerprint across parent sources, all connected module aggregators and members, headers, plan, aliases, and adapter code. A certificate should bind that fingerprint and the verifier/tool fingerprint, as well as the pinned recipe and reviewed evidence hash. The shared full-image gate must still be retail `MATCH`.

## Concrete private evidence

`work/native_lane/slus_partition_genuine/code.json` is a **measurement**, not an authoritative certificate. Its collector row `slus/code` has 156 measured functions and 1,263 words, split into 155 functions/1,254 words in `src/code.c` and one function/nine words in `src/w_80041134_owned.c`. The destination unit's `functions` is `func_80041110`; its `expected_functions` has three names: `func_800410FC`, `func_80041110`, and `func_80041134`. The record reports a retail-exact full-image gate, pipeline self-checks, and zero unmasked retail differences for all 156 row functions. The destination unit's genuine 2.79 **row subset** is exact at nine words; its nested `genuine["2.79"]["physical"]` reports a separate exact 44-word, three-function comparison with retail `{diff: 0, masked: 0, checked: 3}`. By contrast, the 155-function collector remainder has genuine 2.79 diff 47 and retail diff 97. The aggregate therefore has no common exact version. The destination's direct full-TU result cannot certify `slus/code` as a whole.

The private measurement's `physical` field matters: it compares the complete destination object in the same genuine mode as the row-subset measurement. The row-level `exact_versions` and `ownerwise_exact_versions` are narrower summaries and cannot stand in for that full-TU field.

## Minimal proposed input/output contract for primary's schema decision

**Input.** Identify one destination module by manifest name and physical `source`, plus its recipe. Derive the full emitted function set from the current partition plan's destination parts **union** every whole member's functions; reject duplicates, missing functions, or extra emitted functions in the actual object. Record each contributor as `(logical row ID, source, role, function subset)` so the imported collector subset remains distinguishable from whole module members. Bind the connected input fingerprint, tool fingerprint, plan/alias state, reviewed evidence document and reviewer, pinned Ninja recipe hash, and retail-image hash. Read the real compiled destination object and genuine 2.79 result, not a collection of independent one-function rebuilds.

**Proof checks.** Require the full image to match retail; actual destination object source/recipe/coverage to equal the declared physical owner; pipeline object self-check and `maspsx_physical_retail == {diff: 0, masked: 0, checked: N}`; direct genuine 2.79 `physical.exact is True`, `physical.missing == []`, and `physical.retail == {diff: 0, masked: 0, checked: N}`, with no unknown LNK records. `N` is the complete destination-TU function count, three in the private example. Retain per-contributor subset results and mode, but never replace the full physical comparison with their union. If an accepted compiler model is needed, label its exact function scope and distinguish modeled equality from direct equality.

**Output.** A versioned destination-physical certificate could carry `module`, `physical_source`, `physical_recipe`, `expected_functions`, `contributors`, `physical_object`/genuine proof, `gate`, freshness fingerprints, and `review`. Keep any data-ownership receipt as a separate referenced proof with its exact sections/symbols/VMAs; it must not be interpreted as L4/L5 placement. On validation, a destination certificate can support placement only for named module-member rows after their own row checks and the normal ladder. It may record the moved collector function as a proved **part**, but must not emit a placement grant for the collector parent ID. That parent would need a separate complete proof across its remainder and every destination, plus its own source/toolchain criteria.

This contract is deliberately scoped to the destination physical TU. It does not decide the certificate schema, who may review it, or whether a moved collector part should eventually receive a separate sub-row placement status.
