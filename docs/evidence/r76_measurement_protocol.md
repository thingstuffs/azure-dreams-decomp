# r76 measurement protocol: a fair model A/B on matched rows (2026-09-23)

Status: PLAN. Nothing here has been built or launched (except the one cluster dry pack
`work/native_lane/r76_cluster_dry1`, built and kitted to prove the mode, never launched).

## Why a re-measurement

- The r73-r75 wave was all retries of older lanes and paid (`python3 tools/lanes/ab_report.py --glob 'r7[345]_*' --ok-only`):
  Opus 5.5 132/215 rows exact (61.4%), gpt-6-astra 70/97 (72.2%), gpt-6-sol 20/106 (18.9%), gpt-6-luna 10/70 (14.3%).
  But the arms were not matched: different rows, different bands, different retry histories, and the Opus token figures
  were the lanes' own guesses (one was 22,000,000). Since then Opus usage is measured (`usage.json`, backfilled for
  all 43 r73 Opus lanes from the Agent tool's task-notifications) and cost is weighted, not raw tokens.
- The questions: which model removes the most pins per unit of usage in each pin band, and what does each band cost?

## Sample sizes

- Full plan: 40 rows per band per arm = 8 packs x 3 bands x 5 arms = **120 lanes, 600 row-serves**.
- Phase A (stop point): packs 1-4 of each band = 20 rows/band/arm = **60 lanes**. `ab_plan.py` draws by a seeded shuffle,
  so packs 1-4 are the same rows whether the plan is 20 or 40 per band.
- What n buys (binary "row exact", SE = sqrt(p(1-p)/n)): at 20 rows/band SE is up to 11 points; at 40 up to 7.9; pooled
  over three bands (120 rows/arm) up to 4.6. So 60-70% vs 15-20% (the r73-75 strong vs weak gap) is resolved per band
  at phase A; 61% vs 72% (Opus vs astra in r73-75) is NOT resolvable per band even at 40, and only marginally pooled -
  compare those two by paired discordance (McNemar on the rows where exactly one of them is exact) and by cost, not by
  the headline rate.
- Expected usage at the r73-75 per-lane means: luna6 ~686k codex tokens/lane, sol6 ~291k, astra ~442k, Opus ~315k
  Agent-tool tokens (measured). Full plan per arm = 24 lanes: luna6 ~16.5M (16.5 weighted units), sol6 ~7.0M (70 units),
  astra ~10.6M (weight TODO), Opus ~7.6M Agent tokens (weight TODO). Phase A is half of that.

## Procedure

1. **Freeze the rows.** No landing, sweep or generator run may change an A/B row until every arm has finished (the
   arms must see the same text; a landed row changes its sha and breaks the pairing). The committed
   `docs/evidence/r76_ab_rows.json` IS the frozen plan: do not re-draw (a re-draw reshuffles every pack once one row
   has changed). Just before the build, check that every row in it is still in `ab_plan.eligible()` at its current
   text; a row that dropped out is replaced in ALL arms or its pack is dropped in ALL arms.
2. **Codex arms** (one pool per arm and band kind; `--no-land` so nothing lands mid-experiment; the runaway caps are set
   far above anything r73-75 saw - max 118.6 min and 1.26M tokens - so they only catch runaways):

       L=$(python3 -c "import json;print(','.join(k for k in json.load(open('docs/evidence/r76_ab_rows.json')) if k.startswith('r76_luna6_b') and not '_b8c_' in k))")
       python3 tools/lanes/pool.py r76_luna6 --model luna6 -c 3 --rows-json docs/evidence/r76_ab_rows.json --lanes $L \
           --kit --exemplars 6 --no-land --wall-cap 180 --token-cap 3000000
       # the 8+ lanes: the same with --lanes <the _b8c_ lanes> --cluster 3-5
       # sol6: add --paragraphs residual_to_form;  astra: --model astra

   `--served-guard tier` is pool.py's default (round 76); the eligible filter means it refuses nothing. `--band-stop`
   stays OFF during the A/B: it would stop arms unevenly and unbalance the pairing.
3. **Agent-tool arms** (Opus, Sonnet), per lane:

       python3 tools/lanes/build_class_pack.py <lane> x --rows <the lane's rows> --duck --exemplars 6 \
           --served-guard tier --tier opus [--cluster 3-5 for _b8c_ lanes]
       python3 tools/lanes/kit_pack.py <lane> --tier opus
       python3 tools/lanes/record_usage.py --prompt <lane>      # the Agent prompt (no self-estimated tokens)

   Launch with the Agent tool (`model: "opus"` or `"sonnet"`, background), at most 3 in flight per arm, the lane
   prompt exactly as printed. **At each completion** record the harness's figures, never the lane's:
   `python3 tools/lanes/record_usage.py <lane> --tokens <subagent_tokens> --tool-uses <tool_uses> --duration-ms <duration_ms>`
   (from the task-notification's `<usage>` block), or once at the end
   `python3 tools/lanes/record_usage.py --backfill ~/.claude/projects/-home-david-azure-clean/<session>.jsonl --lane-glob 'r76_*'`.
   The Agent tool has no wall cap: the orchestrator stops a lane past 180 min (TaskStop) and writes `cap.txt` itself.
4. **Read out:** `python3 tools/lanes/ab_report.py --glob 'r76_*_b12_*' --glob 'r76_*_b37_*' --glob 'r76_*_b8c_*' --ok-only`
   (not `r76_*`: other r76 work, e.g. `r76_clones*`, shares the prefix), and per band with one glob. Report per arm and band: exact rows, pins removed, wall-min per exact row, tokens (measured only; `~` estimates
   excluded), weighted cost per exact row and per pin, caps fired.
5. **Land after the readout:** one candidate per row (most pins removed; tie -> the cheapest arm) through the usual
   isolated landing (`tools/lanes/land_finished2.sh`). Landing only after all arms keeps every arm's text identical.

## Metrics and what is still missing

- exact rows (byte-exact candidate staged with `.base_sha`), pins removed on exact rows, wall-minutes per exact row
  (lane wall clock; codex lanes from lane.pid to last_message, Agent lanes from the harness's duration_ms).
- weighted cost = tokens x weight / 1e6 (`config/model_cost_weights.json`): luna 1, sol 10 (owner, 09-23). **astra,
  Opus and Sonnet weights are TODO** and must be set by the owner before cross-model cost is compared. Codex and Agent
  token figures are different units (codex: uncached input + output; Agent tool: about the final context size), so a
  Claude weight must be stated per Agent-tool token. A way to measure the codex ones: every codex rollout
  (`~/.codex/sessions/.../rollout-*.jsonl`) logs `rate_limits.primary.used_percent` with each `token_count` event; the
  delta over an arm run ALONE (no other codex lane in the window) divided by its tokens gives drain per token per model.
- Exact-rate differences below ~15 points per band are noise at these n; the protocol's decisions should be about
  cost per pin by band (which model to feed which band), where the r73-75 gaps are several-fold.
