# Type consolidation pilot (r78) - design

Model: claude-opus-5-5[1m]. Lane: `work/native_lane/r78_types_pilot/`. Nothing under src/, include/, config/ or
tools/ was edited; `apply.sh` lands everything under the landing lock (dry run: 243 rows, 0 skipped).

## 1. Data-symbol naming: extend the existing alias layer, add no new mechanism

`config/names.tsv` is already name-agnostic. `tools/build/ccproc.py` builds `{readable: original}` from every row and
rewrites `\breadable\b` on every non-string line of the gcc `-S` output, `.extern` lines included. It does this before
maspsx, `as`, the window link and the SLUS link. `tools/gate/match.py::_canonicalise_names` (the scorer's copy)
does the same. So a data row

    0x8006CCD8  D_8006CCD8  dirStepX  <evidence>

lets C say `dirStepX` while the assembler input still says `D_8006CCD8`. The objects are identical: no relocation
name changes, no absolute symbol is added, and the undefined_syms files are unchanged. Every binary links the same
address because the symbol is still the D_ one.

I checked this against every consumer of names.tsv:

| consumer | data row effect |
|---|---|
| ccproc.py (gate cc.sh, SLUS build via configure.py, verify SLUS path) | canonicalises the name (proven: lane listings through `ccproc --names-only` with the lane table equal the pinned listings, 205/225 steps rows byte-identical text; the rest differ only in `%lo(D_80083460+2)` vs `%lo(D_80083462)` spelling, same bytes) |
| gate/match.py (per-row scorer) | same table, same rewrite. I ran `_canonicalise_names` in-process with the lane table on 4 candidates: its output equals ccproc's byte for byte, and no readable name is left |
| verify.py `canonical_spelling` | only rewrites identifiers the file DEFINES as functions (`name(...) {`), so data names are untouched |
| build/slus_partitions.py `read_aliases` (partitions, row_db, slus_iso, slus_module_context) | skips every row whose canonical column is not `func_XXXXXXXX`, so it is safe |
| gate/overlay_local_gate.py, overlay_func_compare.py | resolve readable -> original by the `(func|D)_<addr>` regex, so they would even link an un-canonicalised name |
| apply_names.py | refuses (`no defining row`): a data symbol has no defining row, so apply.sh appends the rows directly |
| decl_census.py, evidence.py | read the table as aliases; evidence.py documents it as "function renames" (cosmetic) |

Recommended follow-up: an `apply_names.py --data` mode. It would skip the defining-row test, use the same collision
test (the name must not appear as an identifier in src/ or include/), and journal to `ledger/names.jsonl`.

Hazard: a TU that declares both the readable name and its D_ original yields two `.extern D_x,size` lines after
canonicalisation. A migrated row never does this, because its local D_ declaration is removed. SLUS module TUs
(several members in one .s) could do it. slus/w_80042BDC verified exact in its module context, but no module where
two members disagree was exercised.

## 2. Where shared types live

- `include/shared/<object>.h`, one header per object or family (`dir_step.h`, `dungeon_status.h`). The header
  holds the extern with its readable name, the typedef, and the per-field evidence comments.
- The headers use plain C types (`short`, `unsigned short`, `void *`) and include nothing. The first header
  included common.h, and 2 of 231 rows failed to build with it: those rows carry their own `typedef ... u8/s32`
  and never include common.h first.
- Migrated rows include the header explicitly (inserted right after `#include "common.h"`), and each row's local
  copy of the type or extern is removed.
- **Not via common.h yet.** common.h pulls game.h/globals.h into every TU, and local typedef names collide:
  `DungeonStatus` is a local typedef for a different object in dungeon/func_8028B110, and `DungeonGlobals` is one in
  dungeon/func_800BACA4. That is why this pilot's type is `DungeonGlobalStatus`, and apply.sh's preflight refuses
  any collision. Fold the headers into common.h only after a tree-wide collision lint passes, which is the same
  test apply.sh runs.
- `include/records/Rec_*.h` are generated by the struct census ("never hand-edit") and are not the home for
  hand-recovered types. `Rec_D_80083460.h` (span 0x10, 5 functions) is superseded by `dungeon_status.h` and should
  be dropped from the census input when this lands.

## 3. Naming-evidence rule applied

A name must be proven by what the code does, without asserting anything beyond it:

- `dirStepX` / `dirStepY`: the retail bytes are {1,1,0,-1,-1,-1,0,1} and {0,1,1,1,0,-1,-1,-1}. Every row indexes
  them by a direction 0..7 (angle >> 9) and adds them to the entity's grid x byte (+0x24) or grid y byte (+0x25).
  func_807B0110 adds them to the first and second ground axes of a world position. "X/Y" is how the tree already
  spells those axes.
- `DungeonGlobalStatus` / `dungeonStatus`: only the DUNGEON overlay and the SLUS dungeon-entity helper
  (w_80042BDC) touch it. It holds a flag word and counters, so it is named "status", not "state machine" or
  "floor".
- Fields are named only when every use proves the meaning. `flags` (0x02) passes: every use is a bit test or bit
  set. `unk_0A` stays `unk_`, with a comment that it is a counter (+1/-1 at every write), because what it counts is
  not proven. Everything else stays `unk_XX`, with its access census in a comment.
- Randomizer/developer names (docs/SYMBOLS.md) come first when they exist; neither object has one.

## 4. The two recovered types

### 4.1 `short dirStepX[8], dirStepY[8]` (SLUS .data 0x8006CCD8 / 0x8006CCE8)
Access census, 231 rows, from the cc1 listings of the pinned texts, which equal retail order:

- `lh` 496 at 2*d from the table base (signed 16-bit: the values are ±1)
- `lhu` 261 (the load feeds a 16-bit masked add)
- `lbu` 88 (rows that read the low byte for a u8 grid coordinate)
- every table is reached from its OWN lui/addiu (396 + 377 bases)

Two separate arrays, not one `[2][8]`: retail never shares a base between them. The exceptions are 3 rows that
take `D_8006CCD8+16` (the Y table) through one pointer, and those are explicit pointer arithmetic.

### 4.2 `DungeonGlobalStatus dungeonStatus` (SLUS .bss 0x80083460, size 0x20)
Evidence is from 836 rows that touch 0x80083460-0x8008347F: "base" = reached from one lui/addiu of 0x80083460,
"direct" = its own lui with `%lo(D_x)`.

| off | type | evidence |
|---|---|---|
| 0x00 | short unk_00 | lh 2, sh 2 |
| 0x02 | unsigned short flags | lhu 555 (224 base + 331 direct), sh 72; no lh; every use `& 0x2000/0x1000/0x80/0x8` or `|=` |
| 0x04 | short unk_04 | lh 21, lhu 10, sh 34 |
| 0x06 | short unk_06 | lhu 1, sh 3 (sign unproven) |
| 0x08 | short unk_08 | lh 66, lhu 75, sh 77; 2 `lw` (see union below) |
| 0x0A | short unk_0A | lhu 442, sh 406, lh 42 (21 of them direct `lh %lo(D_8008346A)`); A/B below |
| 0x0C | void *unk_0C | lw 92, sw 206; cleared to 0 and compared with a target entity pointer (func_80087A70) |
| 0x10 | void *unk_10 | lw 91, sw 87; assigned `state - 0x20`, an entity (func_800CED34) |
| 0x14 | short unk_14 | lh 5, lhu 6, sh 8 |
| 0x16 | short unk_16 | never accessed |
| 0x18 | unsigned char *unk_18 | lw 12, sw 2 only: a pointer to a byte table (the spawn table, func_8009B140); the rows' `u8 D_80083478[]` declarations are wrong |
| 0x1C | short unk_1C | lh 4, lhu 7, sh 4, lbu 1 |
| 0x1E | unsigned short unk_1E | lhu 15, sh 2 |

- **Extent.** Nothing in 0x80083480-0x80083497 is ever accessed. 0x80083498 is a separate object: 641
  references, 326 of them passing its address, plus the town rows. 0x800834B8 is another one.
- **Size.** slus/w_80042BDC, compiled with -G16, forms a lui/addiu (not $gp) base. That proves the original
  declaration was larger than 16 bytes. 0x20 satisfies every cell.
- **Union 0x08/0x0A resolved.** 0x0A is `short`: at 0x0A, `short` gives 797 exact rows and `unsigned short` gives
  786 (11 rows miss by exactly the one `lh`). Every `lhu` site is a load-modify-store, and gcc loads HImode
  zero-extended whatever the sign. The two 32-bit `lw` at 0x08 are one site in func_8009D47C, which tests
  0x08..0x0B together (`unk_08 || unk_0A`). It is kept as `*(s32 *)&dungeonStatus.unk_08` at the use, and the field
  type stays `short`.

## 5. Codegen hazards measured

1. **Shared %hi (split cells: 2.7.2-cdk, 2.8.x).**
   - A struct member `g.f` whose address is reused compiles to a base, `lui/addiu &g` then `op off($r)`. A single
     use compiles to `lui %hi(g+off)` / `op %lo(g+off)`, which is the same bytes as a separate symbol.
   - Retail's lui pattern in all 836 rows is consistent with ONE struct. With plain field spelling, 234/234
     automatic rows and 20/20 sample rows are exact, including the D2 rows that had two separate symbols' luis in
     one function (different basic blocks, so cse never merges them).
   - The spelling decides the result, not the struct. A pointer-cast view `((u16 *)&dungeonStatus)[5]` compiles
     to the `%hi(g+10)` direct form and misses. All 53 automatic failures were such views: 27 `u16[]`, 21 `s32[]`,
     4 `s16[]`, 3 `u8[]`. The natural `dungeonStatus.unk_0A--` is exact on every one tried (8/8).
2. **Non-split cells (stock 2.7.2 / 2.6.3, macro assembler).** A field access becomes `la g+off` / `lhu g+off`.
   Retail rows func_800A065C and func_800A4DA8 (registered 2.7.2-G0) instead show `la g` + `off($r)`, which is the
   split form. With the struct, both rows' natural one-line spelling is exact at 2.7.2-cdk-G0. The pinned text is
   not exact there (total 6 and 7), so this is a rule-4b / 09-24 coherence repair that removes an `ASM_KEEP` pin
   and a `do {} while (0)` scaffold. It was not landed here.
3. **Signedness.**
   - 0x0A, above.
   - Steps: the plain `short` spelling is exact on 215 rows, including rows that declared the tables `u16[]`.
     10 rows keep `((u16 *)dirStepX)[i]` because their `lhu` feeds a comparison or shift.
4. **-G / small data.**
   - cc1 marks an extern small when its declared size is at most -G. 2.7.2-cdk rows at the default -G8 then emit a
     `la` macro instead of explicit lui/addiu.
   - dungeon/func_800B0770 declared the step tables `s8` (1 B), and retail matches that `la` form. It is not exact
     with `short[8]` (16 B), so it is refused and keeps its local declaration.
   - Every shared type must stay larger than the largest -G of its rows. The step tables and the block are both
     above 16 B.
5. **Byte views.** dungeon/func_80D3CBF8 (2.8.1-G0) reads the tables as `u8[16]`. The cast view changes a
   register choice (9 differences), so the row is refused.
6. **Aggregate copies / alignment.** Neither object is ever copied (no lwl/lwr, no block moves), so this was not
   exercised. Watch for it when a struct replaces an array that is copied (`D_800814A0`?).
7. **SLUS object identity.** `%lo(D_80083462)` -> `%lo(D_80083460+2)` changes a relocation's symbol, not its
   bytes. Overlay rows are byte-compared, so this is fine. A SLUS row with that change needs
   `verify.py --rebaseline-slus` after the SLUS gate. The one SLUS row here keeps the base form, so its listing is
   identical. Its `.extern D_80083460` size changes from 20 to 32 bytes, and verify.py still reports the object
   identical: the undefined symbol's size is not emitted or is masked.
8. **Non-split cells are not byte-invisible.** A load+store of one field in stock 2.7.2 CSEs the field address
   into `la g+off` / `op 0($r)`. Retail's `la g` / `op off($r)` is the split form (hazard 2).

## 6. Scaling recommendation

- **Per-object batches.** A batch is one object and all of its rows, landed through one apply.sh-style script
  (one gate_all plus one SLUS build per batch).
  1. Census the pinned listings (tools/census.py + flow.py: about 3 s for 1,122 rows).
  2. Take widths and signs from retail, and resolve unions with a field-type A/B over the rows.
  3. Run the automatic rewrite to plain fields (`rewrite_blk(loose=True)`), then verify.
  4. Fall back to the view spelling.
  5. Hand-write the natural spelling for the remaining array-view rows.
- **Cost measured.**
  - Automatic rewrite plus verify: 231 rows in 41 s and 857 rows in 2.5 min (6 workers), about 0.2 s of wall time
    per row, with no model involved.
  - Hand natural spelling: 13 rows in this pilot, a few minutes of agent time each.
  - Hit rates without hands: steps 225/229 (98%); block 797/857 (93%, 100% of rows whose declarations match a
    field). The remaining ~7% are array-index views.
- **Next generator.** Map `D_base[i]` / `((T *)&g)[i]` to the field at `i*sizeof(T)`. That turns the 53 view rows
  into natural field accesses; the hand spelling was exact on 8 of 8 of them.
- **Next objects,** by reach:
  - D_800814A0 (723 rows, all binaries; it is the ORed-flags word, and SLUS -G8 rows use $gp, so watch hazard 4)
  - D_80083228 (578)
  - D_80083498 (641 references, town + dungeon, passed by address: its layout comes from callee arguments)
  - D_80083160 (403, all binaries)
- **Readability pass afterwards.** The step rows still carry m2c byte arithmetic
  (`*(s16 *)((u8 *)dirStepX + direction * 2)`). Now that the type is shared, a generator can turn those into
  `dirStepX[direction]`, verified per row.
