# Final CD eight-function source review

I reviewed the seven final members, generated F240 part, owner aggregator, module entry, shared cohort header, and measured `receipt.json` against the earlier cohort trials and current production sources. This review made no changes to measured inputs and ran no build. Exact SHA-256 hashes are in `final_source_review.json`.

The combined translation unit resolves the two earlier integration conflicts. `cd_command_state_owned.c` defines the 11 data objects once, includes seven definition-free members, and declares one `D_800814D3[2]` base view. E758 retains its separately named `__asm__` aliases for the same symbol; F368 and F624 use the common base declaration. F240 uses the shared `SlusCdQueueEntry` type and reads byte zero. The module lists one named data piece for each of the 11 definitions (35 bytes total); each declared byte sequence matches the corresponding `build_slus/assets/54240.bin` slice. This is a proposed owner and exact data carve, not evidence of historical adjacency or ownership beyond those pieces.

The final E758 replaces `&active_queue[head_index]` in the completion lookup with a local byte offset computed as `((head_index << 1) + head_index) << 3`. For its nonnegative byte-derived index, this is exactly `24 * head_index`, the shared queue stride. The explicit local changes value lifetime and allocation, not the selected entry. It also replaces the old 40-byte `S_80083164` padded declaration with a two-byte observed prefix declared as an incomplete array; only element zero's `unk0` is read. The shared driver remains a 12-byte observed prefix, and its declaration makes no enclosing-allocation claim. E758's `D_800814D1[1]` comment now describes a byte view instead of claiming a size-driven address mode.

F368 replaces 16-byte padded aliases at `D_80081451` and `D_80081452` with `[2]` and `[1]` byte views. It reaches `D_80081450` through `(u32)D_80081451 - 1`, and reaches the prior byte of `D_80081452` through `(u32)D_80081452 - 1`; `D_80081451[1]` names that same byte at `D_80081452`. These are correct target addresses for the eight-byte result buffer and retain the retail access widths. The integer-to-pointer conversions rely on the target's 32-bit address representation and are not portable C. The earlier `ASM_REG("$2")` pin in F368 remains; E758's earlier `ASM_REG("$3")`, `ASM_KEEP_NV`, and named assembler-symbol aliases also remain. I found no new padding, register pins, inline assembly, or assembler exceptions in the final delta.

F2A4 now takes the shared queue-entry pointer, removing the distinct local struct type. Its offset-4 `u32` lvalues still load twice and store once, matching the retail word accesses. Relative to the old production `volatile` pointer member, this source does not guarantee those distinct accesses in every optimizer context; the measured recipe does emit them, and the ordinary software queue does not by itself imply an MMIO contract. The historical `volatile` intent remains unresolved.

The direct receipt reports eight complete functions and 1,041 retail words with zero masks and zero mismatches for generic and genuine assembly; their 1,041 instruction tokens agree. Stock is exact for six functions but emits 667 versus 698 words for E758 and 109 versus 113 for F368. Thus this source review supports the generic/genuine direct proof only. Full-image placement, outside-object protection, and live production ownership depend on the separate harness. `REPORT.md`'s statement that the builder preserves function bodies refers to its eight frozen candidate inputs; the final E758/F368 bodies do differ from the current production sources as described above.
