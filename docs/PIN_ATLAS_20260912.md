# Targeting the remaining pins

The latest family harvest removed 26 pins, leaving **10,206 pins in 1,633 functions**.
The problem should be organized around repeatable causes, not 10,206 individual model
sessions. More CPU is useful when it produces reusable evidence or explores a new
mechanism; repeating the same exhausted mutation menu has declining returns.

## What the evidence currently supports

- Joint erasure is real: individually necessary constraints can become unnecessary
  together. The latest variable/family pass removed 22 pins in 79 search CPU seconds;
  its follow-up removed another four. This is selected search yield, before gate costs.
- More brute-force budget alone is weaker: the second mutation harvest yielded about
  17 staged pins per CPU hour versus 39 in the first. The unchanged fence search
  produced no removals in 425 full verifies. These populations differ.
- The refreshed historical tables cover only **6,567 current-source sites in 1,203
  functions**. That leaves 3,639 sites without current-source measurements. Even the
  matching records lack a complete recipe identity. Do not silently reuse them as
  authoritative measurements under today's toolchain.
- Among the 6,372 measured non-marker sites, 25 macro-family/residue categories cover
  80%. Detailed signatures need 1,113 categories for the same coverage. Twenty or
  thirty broad causes are plausible; twenty or thirty universal source rewrites are
  unproven. Residue similarity alone does not establish a common fix.
- Pin distribution: 338 functions have one pin, 954 have 2–8, 250 have 9–20, and 91
  have 21 or more. Small functions permit stronger coverage; large functions need
  guided groups rather than exponential subsets.

The old data refreshed without recompilation is retained at
`work/pin_search/current_patterns_20260912.md`. Macro counts are not the sole objective:
no accepted change may replace pins with extra fences, fake dependencies, or dishonest
pointer/integer reuse. Exact bytes still need source review and publication gates.

## What we need to learn

| Question | Measurement | Decision it enables |
|---|---|---|
| What does each current pin change? | Erase each pin from frozen source, score against retail, retain full aligned regions and static source facts. | Rank representative packets by affected instructions, value role, and compiler configuration. |
| Can instruction overlap predict useful groups? | Compare high-overlap pairs with independently sampled uniform pairs in the same function. | Spend pair-search CPU on the predictor only if it improves exact yield or below-both-single damage. |
| Which groups require more than two removals? | Probe the full set, bounded neighborhoods from measured interactions, and variable/macro groups. | Build group search from verified interactions instead of line proximity alone. |
| Is a repeated mismatch source-, compiler-, or assembler-owned? | Follow a representative from retail instructions through source lifetimes and compiler/assembler output. | Route to a reusable C generator or a toolchain investigation; do not infer ownership from the cluster label. |
| Does a discovered fix transfer? | Freeze a holdout of different functions before changing a generator; report successes and failures by cohort. | Scale the generator only when transfer is demonstrated. |
| Are we reducing total work? | Track staged/landed pins, fences, full scoring CPU, gate wall time, and model time separately. | Optimize the whole harvest, not a favorable search-only rate. |

The first three questions are the CPU experiment. Compiler ownership and transfer need
small, evidence-rich human/model investigations afterward. The atlas produces
hypotheses, not proof that all members of a descriptive cluster share a cause.

## Experiment and durability

`tools/pin_atlas.py` runs a read-only, frozen-source experiment. Every baseline and
candidate is scored against the target through the existing full scorer; negative
results are not filtered through the imperfect cc1 screen. It measures all single
pins, up to 12 uniform pairs and 12 overlapping pairs per function, then up to eight
larger groups. The arms can share pairs, which are compiled once and tagged with both
memberships. Missing ranges are unknown, not evidence of overlap. Uniform selection is
deterministic and independent of the overlap ranking. Pair budgets do not exhaust
large functions, and LCS overlap does not prove causal dependence.

Each probe is saved atomically and bound to source, row metadata, options, environment,
tool code, compilers, references and recipe. Resume reuses finished probes even when a
row summary was interrupted. Failed probes remain explicitly failed; `--retry-errors`
is required to retry them. A 90-second per-probe process-group timeout bounds compiler
hangs. Detached controllers and child-parent death handling prevent closing the
terminal from losing the run or a killed controller from orphaning compiler jobs.
The shared controller lock prevents a competing pin-search publication. Do not rebuild
`build_ovl` or change recipe/tool inputs while the run is active. Identity is rechecked
at completion; recipe drift invalidates the run rather than mixing measurements.

All eligible stock source is included, including one row with an inline-asm blocker;
this is diagnosis, with no automatic publication. Candidates preserve unscored C and
are saved separately. Each exact subset is independent: the union of two exact subsets
is not assumed exact. SLUS uses the existing pinned-object distance; overlay rows use
aligned LCS. Pair comparisons stay within a function.

Eight focused tests cover independent control sampling, unknown/late/insertion ranges,
bounded group selection, manifest changes, probe reuse, explicit error retry, candidate
preservation, and interruption before a row summary. The existing 46 pin-search tests
also pass. The real 12-row pilot completed 289 probes over 87 pins with no errors: 215.4 CPU
seconds and 83 elapsed seconds. It found no removals; the pair samples are too small
to judge the predictor. The full population permits at most 35,486 planned probes,
about 7.35 CPU hours at the pilot rate. Larger functions can cost more. The production
wrapper additionally confines scorer-created temporary files to each probe directory
and restores an exact candidate if interruption occurred after its receipt was saved.
The recipe also binds the generated gate tools and row tables actually executed.

Commands (inspect state before starting or resuming):

```sh
python3 tools/pin_atlas.py prepare --tag pins_atlas_20260912
python3 tools/pin_atlas.py start --tag pins_atlas_20260912 --workers 4
python3 tools/pin_atlas.py status --tag pins_atlas_20260912
python3 tools/pin_atlas.py report --tag pins_atlas_20260912
# Same start command resumes; add --retry-errors only after diagnosing failures.
```

Evidence lives under the named run's ignored directory. `state.json` records controller
identity and completed rows; `rows/<row>/probes/` preserves every result;
`rows/<row>/candidates/` preserves independently exact erasures; `report.json` ranks
source-fact/residue groups and compares the pair arms. A nonzero candidate count is a
staged opportunity, not a landed reduction. The production tag's actual start and pilot
measurements are recorded below once validated.

## Actions after the experiment

1. Review and gate the best exact subset per function. Re-run cheap single erasures on
   staged winners before publication, since the family harvest exposed that opportunity.
   Combine follow-up and comment cleanup into the same publication transaction to avoid
   the repeated expensive window rebuilds seen in this harvest.
2. Choose the top three well-supported recurring mechanisms, allowing one exploration
   sample outside the top groups. Read representative retail sites and source value
   lifetimes; use the existing wall-deconstruction/C-rebuild workflow when applicable.
3. For each mechanism, write an explicit hypothesis, the source conditions it requires,
   a small mechanical generator, and a separate holdout. Keep negative examples. Route
   compiler/assembler-owned cases by evidence rather than widening C mutation budgets.
4. Compare marginal removals per full CPU hour and per model investigation. Expand the
   successful cohort; stop repeating zero-yield searches without a new hypothesis.
5. Refresh only changed rows after landing. Preserve causal evidence by input hash and
   improve cross-batch recipe cache reuse separately, retaining old publication identity.

The 87-row multi-operand selection is retained but deferred. We should not interrupt
this experiment to run another small batch, invalidate its frozen measurement base,
and pay another gate cycle without using what the larger run teaches us.

## First checkpoint and a bounded parser repair

At 13:21 UTC, 214 functions / 1,867 pin sites had completed, using 5,415 probes
and 4,788 CPU seconds. Two functions have independently scored candidate subsets
removing up to four pins. The overlapping-pair arm had three exact pairs and 63
pairs below both single-erasure distances out of 1,387 tested; the uniform arm
had zero exact and 22 below-both pairs out of 1,647. These are preliminary,
within-row sampled results with overlapping arms, not independent population rates.
No candidate has been published from the atlas.

One early function reported two failed probes. Investigation found a parser issue:
`INLINE_STMT_RE` matches `ASM_KEEP` inside `LEGACY_ASM_KEEP`, and erasure leaves
`LEGACY_` behind. Correcting the span in isolated copies of
`dungeon/func_81811F54` makes both its keep-only and combined register/keep erasures
compile normally; both have aligned distance one, so neither is a removal.

An explicit scan of current row pin spans found ten such partial-identifier sites
in six functions. Inspecting the local macro definitions and calls also found five
sites absent from the existing count: three `LOCAL_ASM_REG` declarations, one
`LEGACY_KEEP`, and one `LEGACY_MEMORY_BARRIER`. These are existing scaffolding,
not regressions or new pins. Thus the reported 10,206-site census is known to omit
at least five alias sites; census coverage must be corrected separately from yield.
All seven functions are already eligible for the atlas; its current site enumerator
omits these five additional sites.

**Queued after the frozen atlas:** fix identifier boundaries and recognize the
reviewed full alias tokens by their actual definitions, including input-only versus
read/write keep semantics. Add parser/eraser and NON_MATCHING tests, then replay the
seven affected functions and correct the census. Keep the original failed probes
as evidence. This issue does not invalidate other probes and does not justify
restarting the ongoing full run. No parser, source, or build input changed mid-run.

Evidence and exact queued steps:
[pin_alias_audit_20260912.json](evidence/pin_alias_audit_20260912.json).

## 13:58 checkpoint: workers progressing, counter exception diagnosed

Completed row artifacts now cover 570 functions / 4,573 sites: 13,487 probes and
12,419 CPU seconds, with candidate subsets removing up to 23 pins. The overlap arm
has 11 exact pairs / 3,423 tested and 151 below both single costs; the uniform arm
has two exact / 4,243 and 54 below both. Three rows have failed probes, including
known alias cases. These remain preliminary and no candidates are landed.

`state.json`'s counter stopped at 224 although result files continued to arrive.
The 100-pin `dungeon/func_807B0B3C` names its full-strip probe with 294 filename bytes,
exceeding the filesystem's 255-byte component limit. Its baseline, all 100 singles
and 24 pairs are already saved. This is the only manifest row whose full-strip name
exceeds the limit. The exception exits the result-collection loop, but Python's
executor context waits for all submitted jobs before reporting it; the four workers
continue completing the queued functions. Do not interpret that stale counter as a
stopped job or restart the work.

A detached supervisor, `work/pin_search/pins_atlas_20260912/recover_long_name.py`,
waits on a pidfd for the original controller (no polling loop). It requires the
expected filename error and exactly the diagnosed unfinished row, then resumes
that row with deterministic hashes for overlong numeric artifact basenames only.
Short filenames, candidate bytes, probe identities and frozen atlas code stay the
same. It validates the recipe and every row/probe identity before producing the
complete report and state; the original error state is retained separately. Any
unexpected condition stops this recovery explicitly. Inspect `recovery_state.json`
and the actual supervisor process as well as the original controller when resuming.

After completion, promote bounded artifact names into the atlas and test them with
100-site groups. Also handle per-row future exceptions during collection so an
isolated failure cannot freeze the progress counter while other workers run. Keep
that implementation separate from the frozen experiment and the alias-parser fix.

## Repairs tested in isolation while the atlas runs

Commit `1829aa76` in the detached sparse worktree
`work/pin_search/atlas_tool_fixes_20260912` is ready to absorb **after** the atlas
and its recovery complete. The primary worktree's frozen tools remain unchanged.
It recognizes full local/legacy alias tokens only when their definitions match
reviewed empty-asm forms, respects definition/redefinition/undef position and
NON_MATCHING arms, and distinguishes input-only constraints from read/write keeps.
The standard inline matcher now requires an identifier boundary. Register aliases
and the empty memory barrier are included in the census.

The same commit bounds large-group artifact names, records future exceptions while
continuing progress collection, and makes `status` count atomic row results directly.
Validation: 46 existing search tests, 11 atlas tests and seven alias tests pass
(**64 total**). New cases reproduce the 100-site filename limit, progress continuing
after a failed future, stale status counters, full alias-token erasure, constraint
semantics, definition scope and protected port arms. Real candidate replay remains
pending until the main toolchain can be used after the frozen experiment.

A census of all 1,633 frozen inputs under the repaired parser gives **10,211 sites**,
exactly five more than the old 10,206 count; the number of functions is unchanged.
All seven affected functions erase their recognized pin sites completely in the
parser checks while preserving unscored C. This is coverage correction, not source
changes or removal yield. Validation details are retained at
`work/pin_search/atlas_alias_audit_20260912/isolated_fix_validation.json`.
